zinet

The graph.yaml intermediate representation shared across the ZiNets ecosystem.

It plays the role that LLVM IR plays for compilers: front-ends emit it, back-ends consume it.


wen.gong.research@gmail.com

https://github.com/digital-duck/zinet
zinet is a small Python package that defines one graph format and the tools around it. Several apps in the ZiNets ecosystem share it. This talk covers why it exists, how the format works, and what the package does today.

Outline

    The outline lists every slide title; click a line to jump.

    The problem: every app had its own graph code

    • SPL, ConceptBook, Graph-Code, GraphLang, work-graph and Solver all describe dependency graphs.
    • graph-code and ConceptBook each had their own copies of the graph algorithms.
    • GraphLang and work-graph each had their own drawing code.
    • work-graph had its own comment-preserving YAML round-trip.
    • So the same work lived in several repos, and the copies did not always agree.

    Apps in the ecosystem

    SPL ConceptBook
    Graph-Code GraphLang
    work-graph Solver
    Every app in the ecosystem works with a graph of things that depend on other things. Several of them wrote their own algorithms, drawing code or YAML handling, and those copies drifted apart. zinet moves that shared code into one place.

    The idea: one IR, front-ends and back-ends

    • Front-ends emit graph.yaml.
    • Back-ends consume it.
    • The shared validator and transforms are written once, in zinet.
    • Only the core checks live here. Domain rules, such as solver bounds, belong in the back-end.
    • Other repos depend on zinet, so a change in behaviour affects them too.

    Like LLVM IR

    front-end → graph.yaml
    graph.yaml → validate, diff, slice
    graph.yaml → back-end
    The model is a compiler IR. Apps write the graph, other apps read it, and the generic checks and transforms sit in the middle. zinet keeps out of domain knowledge on purpose.

    Origin: Chinese characters as decomposition graphs

    • Every Chinese character breaks down into radicals → strokes → abstract primitives.
    • That breakdown is a directed acyclic graph.
    • The same reductionist habit appears in physics: protons → quarks → fields.
    • ZiNets applies that shape to knowledge, code, computation and optimization.

    The shape

    primitives: atomic, cannot be broken down
    concepts: built from primitives and other concepts
    applications: the capstone uses
    ZiNets began with a character explorer. A character decomposes into smaller parts, and those parts form a DAG. The same three-level structure turned out to fit the other domains as well.

    Three layers: primitives, concepts, applications

    version: "1.0"
primitives:            # leaves: must not have deps
  - id: x_units
    meta: {type: variable}
concepts:              # built from other nodes
  - id: capacity_constraint
    deps: [x_units, max_units]
    edge_types: {max_units: constraint}
    meta: {expression: "x_units <= max_units"}
applications:          # nothing may depend on these
  - id: minimize_cost
    deps: [capacity_constraint]
    • Primitives have no deps.
    • Nothing may depend on an application.
    • An optional imports list merges in other files without namespacing, so ids must be unique across imports.
    • A node's layer is the key it is written under, not a field of the node.
    This is the whole format. There are three lists of nodes, and each node names the ids it depends on. The rules are short: leaves have no dependencies, applications are terminal, and ids are global across the import tree.

    One schema, many domains

    Toolprimitivesconceptsapplications
    SPLbuilt-in tools (llm_call, api_call)workflow steps, transformsrunnable recipes
    ConceptBookatomic facts, definitionscomposed ideas, theoremscapstone insights, target concept
    Graph-Codeleaf components, APIscomposed modules, servicesdeployable apps, systems
    Solverdecision variables, parametersconstraints, derived quantitiesobjectives, solution targets
    Each domain fills the same three layers with its own kind of node. That shared shape lets one validator and one set of diff rules work across all of them.

    Nodes, deps and edge types

    • Node fields: id, label, deps, edge_types, meta.
    • deps are the incoming edges. An edge runs from a dependency to its dependent.
    • meta is an opaque domain payload. The core never reads, validates or transforms it.
    • Unknown keys are rejected, so a typo like primitves: fails at load time.

    Five edge types

    depends_on (the default)
    data_flow
    prerequisite
    constraint
    inheritance
    A node is small. Edge types only affect rendering and documentation, and validation treats every edge the same way. Domain data goes in meta, and the strict key checking catches mistakes early.

    Validation checks

    ErrorMeaning
    duplicate_idan id is defined more than once
    unknown_depa dep names an id that does not exist
    primitive_has_depsa primitive depends on something
    layer_violationa node depends on an application
    cyclethe graph is not a DAG

    Warning

    orphan: no deps and no dependents

    Optional (off by default)

    not_reducible: --check reducible
    disconnected: --check connected
    --strict runs both
    There are five error checks and one warning. Warnings are printed but do not change the exit code. The two optional checks are off by default, so a graph that is valid today stays valid after an upgrade.

    The zinet CLI at a glance

    zinet validate graph.yaml --strict
zinet diff old.yaml new.yaml        # exit 1 when they differ
zinet slice graph.yaml target_id -o part.yaml
zinet render graph.yaml --format mermaid
zinet prettify graph.yaml --write   # comments are kept
zinet convert graph.yaml            # to graph.json
zinet schema -o schemas/graph.schema.json

    Exit codes

    0 success
    1 validation errors, differences found, or a file not in canonical form
    2 usage, load or render error
    There are seven subcommands. slice writes the target together with everything it depends on. prettify exits 1 when a file is not in canonical form, so it can run in CI. schema exports the JSON Schema for editors and other tools.

    Rendering: six output formats

    FormatNeedsNotes
    svgGraphviz dotthe default, written to stdout
    png, pdfGraphviz dotbinary, so they need -o FILE
    mermaidnothingflowchart text
    htmlnothinginteractive page; works offline
    asciinothingplain-text outline by depth
    Three formats need no extra install. The Graphviz formats need dot on PATH, which you get with apt install graphviz. png and pdf must be written to a file.

    Drawing any networkx graph with zinet.vis

    import zinet
from zinet.vis import render, select, zinet_style
G = zinet.to_networkx(zinet.load_graph("graph.yaml"))
render(G, "graph.html")    # engine="cytoscape" default
sub, note = select(G, node="app", hops=2)
    • Engines: cytoscape (the default, one HTML file that works offline), graphviz, mermaid, ascii.
    • pyvis and graphify are extras: zinet[pyvis], zinet[graphify].
    • A Style maps each app's own attribute names, so no app has to rename anything.
    • select trims big graphs: filters, a neighbourhood, hidden kinds, hub edges, a node cap.
    zinet.vis does not depend on zinet's own format and works on any networkx graph. Engines never read attribute names directly. A Style is a set of small functions that read label, kind, colour, shape, group and edge dashing.

    The interactive page

    • Hover a node: everything except its connections fades.
    • Click a node: its details open.
    • secondary_hidden=True hides the dashed data edges at first, behind a checkbox.
    • groups_collapsed=True shows each group (a LOOP) as one box.
    • Both options are off by default. GraphLang turns both on.

    Layouts

    ✔ Cytoscape.js is bundled in the page
    ✔ If Graphviz is installed, the page uses precomputed open and collapsed layouts
    ✔ default_layout sets the layout the page opens with
    ✔ show_kind=False labels nodes by name only
    The two Style options make the first view of a big graph show only the main flow. Graphviz lays out both the open and the collapsed arrangement, so the collapsed view stays compact. Without dot, the page falls back to its own layouts.

    Shared graph algorithms

    G = zinet.to_networkx(zinet.load_graph("graph.yaml"))
zinet.learning_path(G, "app", known=["a"])
zinet.productivity_order(G)
zinet.reducible(G)       # everything rests on primitives?
zinet.build_order(G)
zinet.gap(G, "app", ["a"])
zinet.ensure_acyclic(G)  # raises CycleError
    • They take a plain networkx.DiGraph with an optional kind attribute on each node.
    • The options reproduce the earlier copies: order=, include_primitives, four reducible rules.
    • The defaults follow graph-code.
    • A missing node raises UnknownNodeError (a KeyError).
    These functions replace the copies in graph-code and ConceptBook. Where the copies behaved differently, an option selects each behaviour instead of picking one. The default is always graph-code's behaviour.

    Comments survive formatting and JSON

    • prettify --write pins each comment to a node id, a key or a section and puts it back.
    • If any comment cannot be put back exactly, the file is not rewritten.
    • convert goes between YAML and JSON. Comments are stored in SQLite: ~/.zinet/comments.db, $ZINET_HOME or --store PATH.

    Removed or renamed nodes

    The comment is written at the end of the file:
    # [orphaned from <id>] ...
    It comes back if the node returns.
    JSON has no comments, so zinet keeps them in a small database while a file is in JSON form. This is the approach work-graph used, and it is the same code, now in zinet.roundtrip. Nothing extra needs to be installed.

    Two graph formats, one family

    GraphLang (graf)

    an executable workflow
    workflow: with nodes: and edges:
    typed nodes with ports, loops, cycles allowed

    zinet

    a static dependency graph
    primitives:, concepts: or applications: as lists
    a DAG in three layers
    • Each tool tells the files apart by content, because the file name is only a convention.
    • Given the other kind of file, a tool names the file type and the command to use, instead of showing a schema error.
    • ConceptBook writes the three layers as mappings with composed_of / needs. zinet does not read that dialect yet.
    GraphLang and zinet both store graphs in YAML, but the graphs mean different things. Merging the two models would force GraphLang's model onto the other apps, so they stay separate and recognise each other's files.

    Characterization tests keep old behaviour

    • Golden files in tests/characterization/golden/ freeze what the sibling apps' copies did.
    • zinet must reproduce them exactly: algorithms, round-trip and vis.
    • tests/characterization/divergences.md records where those copies disagree.
    • golden/graphlang_engines.json is frozen for good, because GraphLang now draws through zinet.

    Regenerating

    tests/characterization/generate.py [--check]
    needs the sibling repos (or ZINET_SOURCES_DIR)
    not part of pytest
    Moving code from several apps into one package risks quietly changing behaviour. The golden files make that a test failure. Where the old copies disagreed, zinet keeps a parameter for each behaviour.

    How to try it

    # from PyPI
pip install zinet

# from source, for development
uv venv .venv && uv pip install \
  -p .venv/bin/python -e ".[dev]"
pytest
    from zinet import load_graph, validate
from zinet import slice_to

graph = load_graph("solver_pipeline.yaml")
for issue in validate(graph):
    print(issue)
prereqs = slice_to(graph, "minimize_cost")
    • load_graph resolves imports but does not validate. Call validate separately.
    • For full test coverage, install dot, node and Chrome or Chromium. Tests that need them are skipped without them.
    Install it from PyPI or from source. Note that some tests skip silently when dot, node or Chrome is missing, so a passing run without them does not cover the interactive page's JavaScript.
