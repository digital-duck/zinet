Your first zinet graph: install, validate, draw

In this tutorial you will install zinet, check a graph.yaml file for errors, and render it as a picture or outline. You need Python 3.10 or newer and a copy of the zinet repository; Graphviz is optional and only needed for svg, png and pdf output.

Step 1: Install zinet

From the repository root, create a virtual environment and install zinet from source with the development extras. Activate the environment, then ask for the version. (If you only want to use the tool, pip install zinet installs it from PyPI.)

uv venv .venv
source .venv/bin/activate
uv pip install -p .venv/bin/python -e ".[dev]"

zinet --version

You should see:

zinet 0.2.1

Step 2: Look at a graph.yaml

A zinet graph has three layers, each a list of nodes: primitives (leaves that must not depend on anything), concepts (composed from primitives and other concepts) and applications (capstones that nothing may depend on). This is the shape of the file:

version: "1.0"
imports: [./shared/tools.yaml]   # optional, resolved relative to this file
primitives:                      # leaves: must not depend on anything
  - id: x_units
    meta: {type: variable}
concepts:                        # composed from primitives and other concepts
  - id: capacity_constraint
    deps: [x_units, max_units]   # ids this node depends on
    edge_types: {max_units: constraint}
    meta: {expression: "x_units <= max_units"}
applications:                    # capstones: nothing may depend on these
  - id: minimize_cost
    deps: [capacity_constraint]

Each node can have these fields:

  • id: unique across the whole graph, including imports.
  • deps: the ids this node depends on (its incoming edges).
  • edge_types: an optional type for a dependency: depends_on (the default), data_flow, prerequisite, constraint or inheritance.
  • meta: a domain payload that the core never interprets.
  • label: an optional human-readable name, used by render.

Unknown keys are rejected on purpose, so a typo such as primitves: fails when the file is loaded.

Step 3: Validate a good graph

Run validate on the solver example that ships with the repository. It prints one line per issue, or an ok line if there are none.

zinet validate tests/fixtures/solver_problem.yaml

You should see:

tests/fixtures/solver_problem.yaml: ok (8 nodes)

The exit code is 0.

Step 4: Validate a broken graph

Save this file as broken.yaml. It has a primitive with a dependency, an unknown id, a cycle, and an isolated application.

# broken.yaml
primitives:
  - id: a
    deps: [b]
  - id: b
concepts:
  - id: c
    deps: [ghost, d]
  - id: d
    deps: [c]
applications:
  - id: app
zinet validate broken.yaml

You should see three errors and one warning:

broken.yaml: error: primitive_has_deps [a]: primitives are leaves but depend on ['b']
broken.yaml: error: unknown_dep [c]: depends on undefined id 'ghost'
broken.yaml: error: cycle: dependency cycle among: c, d
broken.yaml: warning: orphan [app]: not connected to any other node

Errors make the exit code 1. Warnings are printed but do not fail the command. To also check that every concept reaches a primitive (not_reducible) and that the graph is one piece (disconnected), add --strict:

zinet validate broken.yaml --strict

Step 5: Render the graph

render draws the graph from the same file. The html format writes an interactive page that works offline: you can search, zoom and click a node to see its details.

zinet render tests/fixtures/solver_problem.yaml --format html -o graph.html

Open graph.html in a browser. Two other formats need nothing installed and print to the terminal:

zinet render tests/fixtures/solver_problem.yaml --format ascii
zinet render tests/fixtures/solver_problem.yaml --format mermaid

You should see a plain-text outline by depth for ascii, and flowchart text for mermaid. The svg, png and pdf formats need Graphviz's dot on your PATH (sudo apt install graphviz on Debian or Ubuntu). png and pdf are binary, so they require -o:

zinet render tests/fixtures/solver_problem.yaml --format png -o graph.png

Step 6: Cut out the part you need with slice

slice keeps a target node and everything it needs (its prerequisite closure). The next command uses minimize_cost, a node named in Step 2; if the fixture uses other ids, use one of its application ids instead.

zinet slice tests/fixtures/solver_problem.yaml minimize_cost -o part.yaml
zinet validate part.yaml

Check that part.yaml exists, holds no more nodes than the original, and that validate reports it as ok. Without -o, the YAML goes to the terminal.

Step 7: Compare two versions and tidy the file

diff compares two graphs. It prints + id for added nodes, - id for removed ones, and ~ id.field: old -> new for changed fields. It exits 1 when the graphs differ.

zinet diff tests/fixtures/solver_problem.yaml tests/fixtures/solver_problem.yaml

You should see:

no differences

prettify compares a file with its canonical formatting. Without --write it shows a diff and exits 1 if the file would change; with --write it rewrites the file in place and keeps your comments (it refuses if a comment cannot be put back exactly).

zinet prettify part.yaml
zinet prettify part.yaml --write

On a file that is already formatted you should see part.yaml: already formatted.

What just happened

In Steps 3 to 7, each command loaded the YAML into a graph and worked on that one structure. load_graph does not validate, which is why validate (Steps 3 and 4) is a separate step that checks the layer rules: primitives have no deps, nothing depends on an application, ids exist, and there is no cycle. render (Step 5), slice (Step 6), and diff and prettify (Step 7) draw or transform the same loaded graph. The meta field from Step 2 is never read or checked. Exit codes are 0 for success, 1 for validation errors, differences, or a file that prettify would change, and 2 for a usage, load or render error.

Not implemented yet: domain-specific JSON Schema overlays (solver, spl, cba) and spl3 integration. The ConceptBook and graph-code dialect (mappings with composed_of / needs) is not read. GraphLang *.graph.yaml workflow files are a different format; zinet reports them as such and names the command to use instead of giving a schema error.
