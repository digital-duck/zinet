zinet: user guide

zinet is the Python package and zinet command for graph.yaml, the intermediate representation (IR) shared across the ZiNets ecosystem: a schema, a validator and graph transforms. It is for developers and tools that emit or consume static dependency graphs (SPL, ConceptBook, Graph-Code, Momagrid, Solver domains). It is not for running workflows: it persists a graph and runs nothing. GraphLang (graf) workflows are a different kind of graph.

Installation

From PyPI:

pip install zinet

From source, for development:

uv venv .venv && uv pip install -p .venv/bin/python -e ".[dev]"
zinet --version

The tutorial shows zinet 0.2.1 as the version output.

Quick start

A graph has three layers, each a list of nodes. Save this as graph.yaml:

version: "1.0"
primitives:
  - id: x_units
    meta: {type: variable}
concepts:
  - id: capacity_constraint
    deps: [x_units, max_units]
    edge_types: {max_units: constraint}
    meta: {expression: "x_units <= max_units"}
applications:
  - id: minimize_cost
    deps: [capacity_constraint]

This graph is deliberately incomplete: max_units is used but not defined, so zinet validate reports an unknown_dep error for it. Add - id: max_units under primitives to fix it.

Validate the bundled solver fixture:

zinet validate tests/fixtures/solver_problem.yaml
tests/fixtures/solver_problem.yaml: ok (8 nodes)

Then render it:

zinet render tests/fixtures/solver_problem.yaml --format html -o graph.html

Architecture

A YAML file is read by io.load_graph into the Pydantic Graph model. The validator, the transforms and the renderers all work on that model. algorithms.to_networkx converts it to a networkx.DiGraph, which zinet.vis can draw. The zinet command ties these together.

flowchart LR
    Y["graph.yaml"] --> IO["io.load_graph"]
    IO --> S["schema.Graph"]
    S --> V["validator"]
    S --> T["transforms"]
    S --> R["render"]
    S --> A["algorithms"]
    A --> VIS["vis"]
    Y --> P["prettify / roundtrip"]
    CLI["cli"] --> IO
    CLI --> P
  • schema.py: Pydantic models Graph, Node, Layer, EdgeType.
  • dag.py: topological order and ancestors, domain-agnostic.
  • validator.py: structural checks that produce a list of issues.
  • io.py: load_graph (with imports), dump_graph, to_yaml.
  • prettify.py: canonical formatting for zinet prettify.
  • roundtrip.py: comment-preserving YAML, the SQLite comment store, and zinet convert.
  • transforms/: diff_graphs and slice_to (diff.py, slice.py).
  • algorithms.py: graph algorithms on a plain networkx DiGraph.
  • render.py: DOT and Mermaid generation for zinet graphs; svg/png/pdf via dot.
  • vis/: drawing for any networkx graph (engines, select, Style).
  • formats.py: recognises other graph files by content.
  • cli.py: the zinet command.

Concepts

Three layers

Every node lives in exactly one layer, named by the key it is written under.

LayerRoleDependency rule
primitivesIrreducible leaves: tools, parameters, variablesMust have no deps
conceptsIdeas, steps or components composed from other nodesMay depend on primitives and concepts
applicationsCapstones: recipes, systems, objectivesMay depend on any layer, but nothing may depend on an application

Nodes and fields

FieldMeaning
idRequired, non-empty. Unique across the whole document, including imports.
labelOptional human-readable name, used by render.
depsIds this node depends on (its incoming edges). Default [].
edge_typesOptional mapping from a dep id to an edge type. Each key must appear in deps.
metaOpaque domain payload; the core never reads it.

Unknown top-level keys and unknown node keys are rejected, so a typo such as primitves: fails at load time. Domain data goes in meta.

Edge types

An edge runs from a dependency to the node that lists it. Without an entry in edge_types, the type is depends_on.

TypeMeaning
depends_onDefault. Generic dependency or composition.
data_flowA value or artifact passes from dependency to dependent.
prerequisiteThe dependency must be understood before the dependent.
constraintThe dependency bounds or defines the dependent.
inheritanceThe dependent extends or specializes the dependency.

Edge types affect rendering and documentation only; validation treats all edges the same.

Imports

imports lists relative paths (resolved relative to the importing file) to other graph files. Their nodes are merged without namespacing, so ids must be unique across the whole import tree.

Two graph formats

zinet stores a static knowledge or dependency graph. The sibling GraphLang (graf) stores an executable workflow in *.graph.yaml. The file name is only a convention, so each tool tells the files apart by content:

  • workflow: with nodes: and edges: is GraphLang.
  • primitives:, concepts: or applications: as lists of nodes is zinet.

Given the other kind, a tool says what the file is and which command to use, instead of a schema error. ConceptBook and graph-code write the same three layers as mappings with composed_of / needs; zinet does not read that dialect yet, but its algorithms and drawing work on any networkx graph.

Comment preservation

prettify --write keeps YAML comments. Each comment is pinned to what it sits next to (a node by id, a key of that node, or a top-level section; a comment block at the top of the file stays on top) and put back into the canonical text. If any comment cannot be put back exactly, the file is not rewritten.

JSON has no comments, so zinet convert stores a YAML file's comments in a small SQLite database and puts them back when the JSON is converted to YAML again. A comment whose node was removed or renamed is written at the end of the file as # [orphaned from <id>] ... and returns if the node does.

Style and select

zinet.vis draws and trims any networkx graph. A Style is a set of small functions that read your attribute names (node label, kind, colour, shape, group; edge label and dashing), so no app has to rename attributes. select cuts a readable neighbourhood out of a big graph.

Commands

Exit codes: 0 success; 1 validation errors, differences found, or a file that needs prettify; 2 usage, load or render failure.

validate

zinet validate graph.yaml [--strict] [--check NAME] [--no-imports]
OptionMeaningDefault
--strictRun both optional checks (reducible and connected)off
--check NAMERun an optional check (reducible, connected)none
--no-importsDo not resolve importsimports resolved

Exits 1 on errors; warnings are printed but do not fail.

diff

zinet diff old.yaml new.yaml

Prints + id for added nodes, - id for removed nodes and ~ id.field: old -> new for changes. Exits 1 when the graphs differ, otherwise prints no differences.

slice

zinet slice graph.yaml target_id -o part.yaml
OptionMeaningDefault
-o FILEWrite the result to FILEYAML to stdout

The result is the target plus its prerequisite closure.

render

zinet render graph.yaml [--format FORMAT] [-o FILE] [--no-imports]
OptionMeaningDefault
--formatsvg, png, pdf, mermaid, html or asciisvg, to stdout
-o FILEOutput file; required for png and pdfstdout
--no-importsDo not resolve importsimports resolved

html is an interactive page (search, zoom, click a node) that works offline. ascii is a plain-text outline by depth. svg, png and pdf need Graphviz dot.

prettify

zinet prettify graph.yaml [--write]
OptionMeaningDefault
--writeRewrite the file in place; comments are keptoff (shows a diff)

Without --write, exits 1 if the file would change, so it can run in CI.

convert

zinet convert graph.yaml [-o FILE] [--store PATH]
zinet convert graph.json
OptionMeaningDefault
-o FILEOutput filesame name with .json (from YAML) or .yaml (from JSON)
--store PATHComment database to use~/.zinet/comments.db, or $ZINET_HOME

Takes a .yaml, .yml or .json file.

schema

zinet schema -o schemas/graph.schema.json
OptionMeaningDefault
-o FILEWrite the JSON Schema to FILEstdout

The stdout default is inferred from the other commands; the README shows only the -o form.

Validation checks

CodeSeverityMeaning
duplicate_iderroran id is defined more than once
unknown_deperrora dep names an id that does not exist
primitive_has_depserrora primitive depends on something
layer_violationerrora node depends on an application
cycleerrorthe dependency graph is not a DAG (self-loops count)
orphanwarninga node with no deps and no dependents
not_reducibleerroroptional (--check reducible): a concept or application with no primitive ancestor
disconnectedwarningoptional (--check connected): the graph is in more than one piece when edges are read as undirected

not_reducible and disconnected are off by default, so a graph that is valid today stays valid. --strict turns both on.

Python API

from zinet import load_graph, validate, diff_graphs, slice_to, dump_graph

graph = load_graph("solver_pipeline.yaml")   # resolves imports
for issue in validate(graph):
    print(issue)
prereqs = slice_to(graph, "minimize_cost")

load_graph does not validate; call validate separately.

The algorithms work on a networkx.DiGraph with edges from a dependency to its dependent and an optional kind attribute per node (primitive, concept, application; none means referenced but never declared). to_networkx(graph) builds one from a zinet Graph.

import zinet
G = zinet.to_networkx(zinet.load_graph("graph.yaml"))
zinet.learning_path(G, "app", known=["a"])   # what is still needed to reach `app`, dependencies first
zinet.productivity_order(G)                  # order that unlocks the most nodes as early as possible
zinet.reducible(G)                           # does everything rest on primitives?
zinet.build_order(G), zinet.gap(G, "app", ["a"]), zinet.applications_of(G, "a"), zinet.restrict(G, nodes)
zinet.ensure_acyclic(G)                      # raises CycleError, naming the nodes on the cycle

Other functions listed in the changelog: is_acyclic, mandatory_subgraph. topological_order and ancestors also accept a DiGraph.

OptionUsed for
include_primitives, include_targetwhich nodes the result contains
`order="topological"\"alphabetical"\"reach"`ordering
weighted_applications, seed_by_reachbehaviour of the code the functions replace
primitive_ancestry, declared, declared_or_listed, named_primitivesthe four reducible rules

Defaults follow graph-code. Errors: UnknownNodeError (a KeyError) for a missing node, CycleError for a cycle.

Drawing with zinet.vis

from zinet.vis import render, select, zinet_style
G = zinet.to_networkx(zinet.load_graph("graph.yaml"))
render(G, "graph.html")                         # engine="cytoscape" (default)
sub, note = select(G, node="app", hops=2)       # filters, hidden kinds, hub edges, a node cap

Examples

A broken graph with a primitive that has a dependency, an unknown id, a cycle and an isolated application:

# broken.yaml
primitives:
  - id: a
    deps: [b]
  - id: b
concepts:
  - id: c
    deps: [ghost, d]
  - id: d
    deps: [c]
applications:
  - id: app
zinet validate broken.yaml
broken.yaml: error: primitive_has_deps [a]: primitives are leaves but depend on ['b']
broken.yaml: error: unknown_dep [c]: depends on undefined id 'ghost'
broken.yaml: error: cycle: dependency cycle among: c, d
broken.yaml: warning: orphan [app]: not connected to any other node

The command exits 1 because of the errors.

Limits

Not yet implemented:

  • Domain-specific JSON Schema overlays (solver, spl, cba).
  • The graph.html interactive explorer, which belongs to cba.
  • spl3 integration (SPL scripts compiling to GraphIR), the stated next step.
  • Reading the ConceptBook / graph-code dialect (composed_of / needs).

Design decisions:

  • load_graph does not validate.
  • Unknown top-level and node keys are rejected.
  • Imports merge without namespacing, so ids must be unique.
  • Only core checks live here; domain rules (for example, solver bounds) belong in the back-end.
